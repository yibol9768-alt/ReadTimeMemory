# Research Proposal：读时编译的记忆（Read-time Compiled Memory）

写于 2026-10-16 凌晨（美东）。数字全部来自 `docs/PROGRESS.md` 里已经跑出的结果。下文“Hindsight”指开源的 Hindsight 1.0.0 记忆系统。

## Problem Anchor（问题锚点，之后每一轮原样照抄）
- **根本问题**：在很长的多会话对话里（BEAM 100K/1M、LongMemEval-S，10 万到 100 万 token），让一个固定的 LLM 读者正确回答依赖历史信息的问题，包括抽取、更新、矛盾、时间、排序、摘要等能力。
- **必须解决的瓶颈**：现有做法丢分，主要不是因为信息没存下，而是读者用不上。
  - 100K 上全上下文 74.4 分，丢的 25.6 分全部是“信息就在上下文里，但答案没用上”。
  - Hindsight 给读者 125K 字，丢分里有 17.8 分属于同类。
  - 把原文还给读者（H33）反而掉 9.7 分（p=0.004）。
  - 另一方面，压成 8K 的记录又会丢掉细节和全局脉络：记录检索的丢分里，写入阶段占 15.7 分，信息抽取 70.8 分（逐字检索是 92.0），摘要 39.6 分（全上下文是 53.9）。
  - 召回的“广”和读者的“窄”现在是绑在一起的：要么给多、读者淹没，要么给少、信息缺失。
- **非目标**：
  - 不训练模型；
  - 不追求更大的上下文窗口；
  - 不做新的检索器或向量模型；
  - 不做 agent 式多轮工具调用；
  - 不以 LoCoMo 为主战场（已经饱和）。
- **约束**：
  - 只用 API 模型。实验读者和判分统一用 gpt-6-luna（Pro 代理）；向量用 H20 上的 qwen3-embedding-8b。
  - 开发集：BEAM-100K 120 题、BEAM-1M 40 题、LongMemEval-S 62 题。测试集在方法定型前不碰。
  - 噪声：BEAM-100K 120 题单次生成，95% 区间约 ±5 分。方法比较要做 3 次生成。
  - 目标 ICML 2027，2027-01 下旬截稿。
- **成功条件**：
  1. 在同一读者、同一判分下，读者看到的上下文 ≤8K 字时，BEAM-100K 上超过全上下文（74.4）；
  2. BEAM-1M 上明显超过 Hindsight 和逐字检索；
  3. LongMemEval-S 上方向一致；
  4. 有消融证明提升来自机制本身，而不是来自更多上下文或更多调用。

## Technical Gap
- **现有流水线断在哪**：所有基线都在“写入时”把对话压成一种固定形态（记录、事实网络、主题摘要），然后在“读取时”把检索到的形态原样交给读者。于是：
  1. 压得越狠，丢得越多（写入损失）；
  2. 给得越多，读者越用不上（读者损失）；
  3. 不同能力需要不同形态（记录利于知识更新和时间，原文利于抽取，广覆盖利于摘要），但单一形态只能顾一头。各方法逐题取最好的上限是 79.2，而最好的单方法只有 69。
- **为什么朴素修补不够**：
  - 加预算：记录 20K 只有 +1.6，不显著；1M 上反而 -4.5。
  - 把原文塞回去：H33，-9.7。
  - 写入时加更多结构：按人汇总 +0.4，加原话锚点 +0.6，都在噪声内。
  - 写入时反复改写还会漂移（我们 10-13 到 10-15 的漂移实验；Zhang 等 2605.12978）。
- **最小够用的干预**：把“编译”从写入时挪到读取时。写入时只做不改写、带出处的账本（我们已有的 Lychee-lite 记录，加上原文轮次）。读取时先广召回（记录 + 原文，几万字），再由同一个 LLM 按“小块读、只抽与题相关的证据”把它编译成一页短证据单。读者只读这页证据单。
  - 广召回补“信息缺失”；
  - 每次只读一小块，避免“读者淹没”；
  - 从账本重新编译，不改写已有记忆，所以没有漂移。

## Method Thesis
- **一句话**：长对话记忆应在读取时、从不可改写的账本按题编译，并把“召回宽度”和“读者负担”解耦：召回可以很宽，读者只看编译后的短证据单。
- **为什么是最小干预**：账本、检索、读者全部沿用已有部件。新东西只有一个“分块证据编译器”（一个提示、一个固定的块大小），加一条规则：读者只读编译结果。
- **为什么合时**：
  - 这是把推理时计算（test-time compute）用在记忆上：精度随读时计算增长，读者上下文不变。
  - 它也解释了为什么长上下文模型并没有让记忆过时：全上下文的读者损失恰恰说明“能放下 ≠ 能用上”。

## Contribution Focus
- **主贡献**：读时编译（Read-time Compilation，RTC）。
  - 对每个问题，先从账本和原文做宽召回；
  - 再按固定块大小，用 LLM 分块抽取与题相关、带日期和出处、保留原样数字和原话的证据；
  - 合并成一页证据单，读者只读它。
  - 配一个可调的“召回宽度”旋钮，得到精度随读时计算增长的曲线。
- **辅助贡献（分析）**：丢分归因方法（写入、检索、读者三类），以及“给读者更多反而更差”的受控证据（H33、全上下文、Hindsight）。这部分用来动机化主贡献，不另起方法。
- **明确不是贡献**：
  - 账本本身（Zep、Lychee 已有）；
  - 摘要指回原文（ReadAgent、LeanMem 已有）；
  - 分层结构（L1）；
  - 多路检索。

## Proposed Method
### Complexity Budget
- **冻结、复用**：
  - Lychee-lite 记录账本（分段、一次编码、不改写）；
  - BM25 + 向量 + RRF 检索；
  - luna 读者；
  - 官方判分。
- **新增**：一个编译提示，加两个超参数：块大小 S（默认 8K 字）、召回宽度 W（默认 40K 字，可调到 160K 或全量）。不训练任何东西。
- **故意不用**：
  - 写入时的结构层（实体状态表、时间线）；
  - 多轮 agent 检索；
  - 学习式路由；
  - 题型分流；
  - 读者自检后再加宽。

### System Overview
```
写入（每个会话一次，不改写）：对话 → 分段 → 记录账本 R（每条带日期和来源轮次 id）；原文轮次 T 保留
读取（每个问题）：
  1) 规划：问题 → 最多 3 个检索查询、实体、时间窗（沿用 lychee.plan）
  2) 宽召回：在 R 和 T 上做 RRF 排序，按排名交错取，直到 W 字 → 候选证据 E（记录与原文混合，各带日期和 id）
  3) 分块编译：E 按排名顺序切成 S 字的块 E1..Ek；对每块并行调用编译器：
       “问题 Q（附当前日期）。下面是记忆片段。逐条列出回答 Q 需要的事实：每条带日期和来源 id；
        数字、时间、名称照原样；若有前后不一致或更新，两边都列出并注明日期；无关就输出 NONE。”
  4) 合并：去掉 NONE，按日期排序、去重，得到证据单 B（目标 ≤8K 字，超出就按块排名截断）
  5) 回答：读者只读 B（以及问题、当前日期），用统一的回答提示
```

### Core Mechanism
- **输入、输出**：输入问题 Q 和候选证据 E（W 字）；输出证据单 B（≤8K 字）。
- **策略**：分块、独立、并行抽取，按日期合并。每次编译调用只读 S 字，所以单次调用不出现长上下文损失。合并后的 B 是“对题编译”的，只含相关事实。
- **训练信号**：无。编译器是同一个读者模型换一个提示（模型自己当自己的编译器）。
- **为什么是主新意**：
  - 把记忆系统的“视图”从写入时的固定形态，改为读取时按题生成；
  - 把召回宽度变成可扩展的推理时计算轴；
  - 并且明确证明了两件事：同一召回集“直接读”不如“编译后读”，读时编译优于写时编译。

### Modern Primitive Usage
- LLM 在这里同时是规划器（已有）和编译器，编译器的角色就是对题证据蒸馏。
- 相比旧式做法（固定 top-k 加重排序器、学习式压缩器）：它不需要训练，能处理“前后矛盾、版本更替”这类需要理解的抽取，而且块大小和宽度可以直接换算成推理时计算。

### Integration
- 写入不变，读取在检索和读者之间插入编译。
- 所有基线（全上下文、逐字检索、记录检索、Hindsight）都可以作为“召回源”接入同一个编译器。所以 RTC 也是一个可以套在任何记忆系统外面的读取层。这一点同时是一个消融：Hindsight + RTC 对比 Hindsight。

### Training Plan
- 无训练。
- 超参数（S、W、证据单上限）只在开发集上选，选定后冻结，再上测试集。

### Failure Modes and Diagnostics
- **编译器漏抽**（在 E 里却没进 B）：沿用错误分析脚本 erran，新增“编译损失”一类，直接测量。
- **编译器幻觉**（B 里有 E 里没有的东西）：抽查 B 的出处 id，检查是否能在 E 里找到。
- **成本**：每题多出 ⌈W/S⌉ 次短调用。报告每题输入 token，并和全上下文（每题 100K 输入）、Hindsight 比较。100K 上 W=40K、S=8K，就是 5 次 8K 调用加 1 次读者，总输入约为全上下文的一半。
- **对摘要类无效**：摘要需要全局覆盖。用宽度曲线检验：W 增大时摘要分应该上升。

### Novelty and Elegance Argument
- **最接近的工作**：
  - Chain-of-Agents（分块 worker + manager，处理长文档）；
  - ReadAgent（gist + 回查原文）；
  - RECOMP、CompAct（RAG 上下文压缩）；
  - LeanMem（按题分配检索预算）；
  - Hindsight（写入时 observations）。
- **差别**：
  1. 用在“会持续增长的对话记忆”，编译的输入是带时间和出处的账本加原文的混合召回。写入侧不改写，与漂移文献（2605.12978）直接对接：写时编译会漂移，读时编译每次从源头来。
  2. 给出受控证据：同召回集下“直接读 vs 编译后读”的差，以及读时编译与写时编译在等成本下的对比。
  3. 召回宽度带来的推理时扩展曲线。
- 整个方法只有一个机制。要把它和 Chain-of-Agents 这类长文档方法区分开，靠的是记忆设定（增长、更新、矛盾、时间）和受控对照，而不是部件数量。

## Claim-Driven Validation Sketch
### Claim 1（主）：在相同召回下，读时编译让读者用上更多信息，并超过全上下文和最强记忆系统
- **最小实验**：BEAM-100K 开发集，3 次生成。
  - RTC（W=40K）；
  - 同一召回集 E 直接给读者读（“直接读”，读者上下文 40K）；
  - 记录检索 8K、全上下文、Hindsight；
  - RTC 套在全上下文上（W=全对话，每题全量分块编译）。
- **指标**：官方判分均分；erran 的读者损失。
- **预期**：
  - RTC 比直接读高（同信息、不同读法）；
  - RTC(全对话) 比全上下文 74.4 高；
  - RTC(W=40K) 读者上下文 ≤8K 时接近或超过 74.4；
  - 读者损失明显下降。

### Claim 2（辅）：读时编译优于写时编译，并且随召回宽度单调提升，在 1M 上保持
- **最小实验**：
  - 写时编译（lychee_roll 汇总、H31/H32 编译式记忆）与 RTC 在相同读者 token 下对比；
  - W ∈ {8K, 20K, 40K, 80K, 160K} 的曲线（100K 和 1M）；
  - BEAM-1M 40 题和 LongMemEval-S 62 题复验。
- **指标**：均分、各能力分、每题输入 token。
- **预期**：曲线随 W 上升后趋平；1M 上 RTC 比 Hindsight 高 ≥5。

## Experiment Handoff Inputs
- **必须证明**：同召回下编译优于直接读；超过全上下文；1M 上超过 Hindsight。
- **必须跑的消融**：
  - 去掉编译（直接读）；
  - 只用记录召回、只用原文召回；
  - 块大小 S；
  - 证据单上限；
  - 编译器“两边都列出”的指令。
- **数据集和指标**：BEAM-100K、1M 官方判分；LongMemEval-S 官方判分。
- **风险最高的假设**：
  1. 编译器自己会漏抽，和读者是同一个模型、同一种失败；
  2. 摘要类无法靠抽取解决；
  3. 收益被“多了调用”解释。对照：直接读和自洽投票（读者多次采样）在等调用数下对比。

## Compute & Timeline Estimate
- **GPU**：无训练；向量服务已有。
- **API**：BEAM-100K 120 题 × 6 次编译调用 × 3 次生成 ≈ 2200 次短调用，每个配置约 1 小时。
- **时间线**：
  - 10-16：试点；
  - 10-17：消融和宽度曲线；
  - 10-18：1M 和 LongMemEval；
  - 之后进入 experiment-plan。
