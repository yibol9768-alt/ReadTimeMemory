# Round 1 Refinement

## Problem Anchor（与 round 0 原样相同）
- **根本问题**：在很长的多会话对话里（BEAM 100K/1M、LongMemEval-S，10 万到 100 万 token），让一个固定的 LLM 读者正确回答依赖历史信息的问题，包括抽取、更新、矛盾、时间、排序、摘要等能力。
- **必须解决的瓶颈**：现有做法丢分，主要不是因为信息没存下，而是读者用不上。
  - 100K 上全上下文 74.4 分，丢的 25.6 分全部是“信息就在上下文里，但答案没用上”。
  - Hindsight 给读者 125K 字，丢分里有 17.8 分属于同类。
  - 把原文还给读者（H33）反而掉 9.7 分（p=0.004）。
  - 另一方面，压成 8K 的记录又会丢掉细节和全局脉络：记录检索的丢分里，写入阶段占 15.7 分，信息抽取 70.8 分（逐字检索是 92.0），摘要 39.6 分（全上下文是 53.9）。
  - 召回的“广”和读者的“窄”现在是绑在一起的：要么给多、读者淹没，要么给少、信息缺失。
- **非目标**：
  - 不训练模型；
  - 不追求更大的上下文窗口；
  - 不做新的检索器或向量模型；
  - 不做 agent 式多轮工具调用；
  - 不以 LoCoMo 为主战场（已经饱和）。
- **约束**：
  - 只用 API 模型。实验读者和判分统一用 gpt-6-luna（Pro 代理）；向量用 H20 上的 qwen3-embedding-8b。
  - 开发集：BEAM-100K 120 题、BEAM-1M 40 题、LongMemEval-S 62 题。测试集在方法定型前不碰。
  - 噪声：BEAM-100K 120 题单次生成，95% 区间约 ±5 分。方法比较要做 3 次生成。
  - 目标 ICML 2027，2027-01 下旬截稿。
- **成功条件**：
  1. 在同一读者、同一判分下，读者看到的上下文 ≤8K 字时，BEAM-100K 上超过全上下文（74.4）；
  2. BEAM-1M 上明显超过 Hindsight 和逐字检索；
  3. LongMemEval-S 上方向一致；
  4. 有消融证明提升来自机制本身，而不是来自更多上下文或更多调用。

> 注：锚点里关于“主要是读者用不上”的表述，审稿人指出过强：全上下文的丢分按定义全记为读者损失；记录检索的写入损失 15.7 大于读者损失 9.6。锚点按规则不改。下面的论证改用更稳的说法：**证据覆盖与读者可用性之间的取舍**。成功条件不变。

## Anchor Check
- **原始瓶颈**：长对话中，读者要么拿不到需要的证据，要么拿到了却用不对。
- **修改后为什么仍然针对它**：
  - 新方法针对的是这个瓶颈里最“记忆特有”的一块：同一件事在时间上有多个说法（更新、矛盾、前后事件）。
  - 现有做法在写入时就裁决（保留一边、合并、作废），丢掉另一边；或者读取时把两边分散在不同位置，读者看不出它们是同一件事。
  - 新诊断（BEAM-100K 开发集，记录检索）：
    - 矛盾题的未满分评分点里，写入时丢了一边的 10 个，两边都在但读者自行裁决的 10 个；
    - 事件排序题里，同线索事件没召回的 12 个，写入丢的 11 个。
  - 这三类能力（矛盾、事件排序、知识更新）也是所有方法的弱项。全上下文分别只有 57.3、65.8、66.7。
- **被视为偏移而拒绝的建议**：无。审稿人明确提醒，不能只做抽取或知识更新、丢掉摘要等能力。新方法覆盖全部能力，只是主机制针对“同一件事的多个说法”。其余能力沿用原流程，并在报告中单列，不剔除。

## Simplicity Check
- **主贡献**：读时裁决的说法链（Claim Chains with Read-time Resolution，CCR）。
  - 写入时：每条记录多标一个“议题键”，表示这条记录在说哪件事；写入时永远不裁决、不合并、不作废。
  - 读取时：把命中议题的全部说法按时间顺序整条带出，摆成“议题 → 时间顺序的说法链”，交给读者，由读者在读取时裁决。
- **删除或合并的部分**：
  - 原来的“分块证据编译器”（RTC）从主贡献降为对照组：它就是审稿人说的通用 map-reduce 压缩，作为“通用压缩”基线保留；
  - 删去“读时编译优于写时编译”和“消除漂移”两个主张；
  - 删去宽度单调提升的预设。
- **拒绝的复杂化建议**：不加全局第二轮编译器，不加图数据库或实体图，不加学习式路由。议题键只是记录上的一个字符串字段，闭包就是“同键取全”。
- **为什么仍是最小够用**：在已有的记录检索上只多两件事：写入时多一个字段（不额外调用）；读取时一次按键展开和按链打包（无 LLM 调用）。读者、检索、预算都不变。

## Changes Made
### 1. 主机制从“通用分块编译”改为“议题键 + 说法链 + 读时裁决”
- **审稿人说**：RTC 是通用的按题 map-reduce 压缩，和 RECOMP、CompAct、Chain-of-Agents 同族。跨块依赖、矛盾两边、截断时把更正截掉，这些问题都没有说清。
- **做法**：把“跨块依赖”变成显式的数据结构。同一议题的所有说法共享一个键，读取时整条链一起进入上下文；截断以整条链为单位，链内不截断。这样更正不会和被更正的原说法分开，矛盾两边也一定同时出现。
- **理由**：
  - 新诊断显示，丢分恰好来自“一边没写下”和“两边分开、读者自行裁决”；
  - 通用压缩器不知道哪些片段说的是同一件事，做不到这一点。
- **对核心方法的影响**：主机制换了，但仍然只有一个机制。

### 2. 写入时不裁决
- **审稿人说**：“从账本重编译所以无漂移”说过头了。
- **做法**：只保留可检验的版本：对比“写入时裁决”（Mem0、Graphiti 式：新说法到来时更新或作废旧说法，读者只见当前版本）和“读时裁决”（全链保留）。不再声称消除漂移。
- **理由**：Mem0 的 UPDATE/DELETE、Graphiti 的作废边，都是写入时裁决。这是领域的主流设计，因此值得做受控对比。

### 3. 验证改成三层对照，冻结证据
- **审稿人说**：缺通用压缩对照；计算量没对齐；目标设成“1M 上比 Hindsight 高 5 分”，其实和现有记录检索差不多。
- **做法**：
  - 同一批记录、同一规划、同一召回，比较：①记录检索；②记录检索 + 通用编译（RTC）；③CCR。
  - 报告每题实际输入、输出 token。
  - 1M 的目标改为超过记录检索（63.3）。
  - 用 3 次生成和按对话聚类的配对检验。

### 4. 表述收紧
- 全上下文的读者损失按定义成立，不再拿它当“读者过载”的独立证据。H33 只说明“那种回原文设计不行”。

## Problem Anchor

## Technical Gap
- **对话记忆和静态文档检索的根本区别**：同一件事会被说很多次，说法随时间变化。例如计划改时间、状态更新、前后矛盾、一件事的多个阶段。
- **现有系统处理“同一件事的多个说法”有两种方式**，都会丢分：
  - **写入时裁决**：Mem0 的 UPDATE/DELETE、Graphiti 的作废边、我们 Lychee-lite 编码器里的消歧状态。新说法来了就改写、作废或忽略旧说法。裁决发生在不知道未来会问什么的时候，裁错了或者只留一边，就无法挽回。
    - 证据：记录检索的矛盾题里，有 10 个评分点是因为一边从未被写下；
    - BEAM 的矛盾题要求“指出矛盾并反问”，写入时裁决后根本答不出。
  - **不裁决但分散存放**：逐字检索、Hindsight、记录检索。同一件事的说法散在不同记录里，召回时可能只拿到一部分（事件排序题检索丢分 12 处）。拿到了也分散在上下文各处，读者看不出它们是同一件事的不同时间版本，于是自行裁决（读者损失 10 处），或者排序出错。
- **为什么朴素修补不够**：
  - 加预算（+1.6，不显著）、回原文（-9.7）、加原话（+0.6）都不改变“同一件事的说法是否被一起召回、一起呈现”；
  - 通用按题压缩（RECOMP、CompAct、map-reduce）按片段独立处理，同样不知道片段之间的“同一议题”关系。
- **缺的机制**：一个显式的“议题”结构。写入时只标注，不裁决；读取时按议题闭包召回，按时间成链呈现。

## Method Thesis
- **一句话**：对话记忆应在写入时只给每条说法标上它所属的议题、永不裁决，在读取时把命中议题的整条说法链按时间呈现给读者，由读者结合问题裁决（取最新、指出矛盾、排序）。
- **为什么是最小干预**：
  - 记录、检索、读者、预算全部沿用；
  - 写入只多一个字段，读取只多一次按键展开和打包，都不额外调用 LLM；
  - 唯一的新东西是“议题键”这个接口和“以链为单位”的打包规则。
- **为什么合时**：
  - LLM 读者擅长在看到完整证据时做裁决，但不擅长在证据缺一边或分散时察觉问题。
  - 把裁决从写入时（无问题、无全局信息）挪到读取时（有问题、有全链），是把 LLM 的推理能力用在它有优势的地方。

## Contribution Focus
- **主贡献**：CCR，包括两部分：
  1. 写入接口：每条记录带议题键 `slot`（规范化的“主体 / 属性或事件线”，例如 `Darryl / 网购球鞋经历`、`Crystal / 遗嘱执行人人选`）；
  2. 读取算法：议题闭包加以链为单位的打包。
- **辅助贡献（分析）**：
  - “写入时裁决 vs 读取时裁决”的受控对比；
  - 丢分归因（写入、检索、读者），把“同一件事的多个说法”这一类单列出来测量。
- **明确不是贡献**：
  - 账本、出处（Zep、Lychee 已有）；
  - 通用按题压缩（RTC 作为对照基线）；
  - 知识图谱；
  - 多路检索。

## Proposed Method
### Complexity Budget
- **冻结、复用**：
  - Lychee-lite 分段、编码；
  - BM25 + 向量 + RRF；
  - 规划器；
  - luna 读者；
  - 官方判分。
- **新增**：
  - 编码提示里加一个 `slot` 字段的说明，以及“不要裁决、两边都记”的规则（删去“消歧状态里裁决”的倾向）；
  - 读取时的闭包加打包函数（纯代码）。
- **故意不用**：
  - 写入时的合并、作废、汇总；
  - 实体图；
  - 第二轮 LLM 编译；
  - 学习式路由；
  - 题型分流。

### System Overview
```
写入（每段一次调用，不改写旧记录）：
  段落 → 记录 {text, time(说话日期), event_time(若明说), speaker, sources, slot}
  slot 规范化：编码器看到当前“议题表”（已出现的 slot 名称，最多 N 个，类似现有消歧状态），
  同一件事复用已有 slot 名称，否则新建。规则：不判断谁对谁错，不删除、不覆盖任何旧记录。
读取（每个问题）：
  1) 规划 + 召回：与记录检索相同，得到记录排名 r1, r2, ...
  2) 议题闭包：按排名依次取记录的 slot；对每个 slot 取账本中该 slot 的全部记录（不限于被召回的）
  3) 成链：每个 slot 一条链，链内按 time 排序，每条标说话日期、事件日期、说话人、来源 id
  4) 打包：按 slot 首次出现的排名，逐条加入整条链，直到 8K 字；
     单条链超过预算上限 B_chain 时，保留首条、末条和与问题最相关的中间条，并注明“中间省略 k 条”
  5) 读者：统一回答提示，加一句“同一议题下按时间列出了全部说法，可能包含更新或互相矛盾的说法”
```

### Core Mechanism
- **输入、输出**：输入问题和记录账本（带 slot）；输出按议题成链的上下文（≤8K 字）。
- **策略**：
  - 闭包保证同一议题的说法一起出现：更正和原说法不分离，矛盾两边同时出现，事件线完整；
  - 链内按时间排序，让“更新”与“矛盾”可以由读者区分（有没有明确的更正语气、时间先后）；
  - 以链为截断单位，避免截掉更正。
- **训练信号**：无。
- **为什么是主新意**：
  - 把“同一件事的多个说法”作为记忆的一等结构；
  - 把裁决从写入时挪到读取时；
  - 并用受控实验证明：写入时裁决（主流设计）系统性地丢掉了读取时才能正确使用的信息。

### Modern Primitive Usage
- 编码器（LLM）负责标议题，读者（LLM）负责读时裁决。两者都是现成模型换提示，不训练。

### Integration
- 只改记录检索的写入提示和读取打包。可以作为任何“抽取式记忆”（Mem0、Hindsight 的事实）的读取层外挂，但论文只在自己的账本上做主实验。

### Failure Modes and Diagnostics
- **议题键过粗**（一个 slot 里塞了很多不相关的事）：链过长，挤占预算。诊断：slot 大小分布；超长链用 B_chain 截断，并报告截断率。
- **议题键过细或不一致**（同一件事分在两个 slot）：闭包失效。诊断：在矛盾、知识更新题上人工抽查两边是否同 slot（开发集 24 题即可）。
- **写入仍丢一边**：用 erran 的“写入”类直接测。
- **读者看到全链仍裁决错**：读者损失。单独报告，因为这部分属于读者提示问题，不是记忆问题。
- **成本**：写入调用数不变（输出多一个字段）；读取无额外调用。

### Novelty and Elegance Argument
- **最接近的工作**：
  - Graphiti/Zep：时间知识图谱，边带有效期，新事实作废旧边。属于写入时裁决，读者默认只见有效边。
  - Mem0：ADD/UPDATE/DELETE，属于写入时裁决。
  - LeanMem：只更新事件类，记录不合并。没有议题链和读时裁决。
  - 通用按题压缩（RECOMP、CompAct、Chain-of-Agents）：不知道片段间的同议题关系。
- **差别**：
  - 写入时只标议题、不裁决；
  - 读取时按议题闭包成链；
  - 并且受控地比较“写入时裁决 vs 读取时裁决”。
- 机制只有一个接口（slot）加一个打包规则。

## Claim-Driven Validation Sketch
### Claim 1（主）：在相同账本、相同召回、相同读者预算下，议题闭包成链优于记录检索，也优于通用按题压缩
- **最小实验**：BEAM-100K 开发集，3 次生成，冻结规划和召回。
  - ① 记录检索；
  - ② 记录检索 + RTC 通用压缩；
  - ③ CCR；
  - ④ CCR 去掉闭包（只成链、不补全）；
  - ⑤ CCR 去掉成链（补全但按排名散放）。
- **指标**：官方均分；矛盾、事件排序、知识更新三类分；erran 的写入、检索、读者损失；每题 token。
- **预期**：③ > ① 且 ③ > ②，主要来自三类能力；其余能力不降。④、⑤ 各自解释一部分。

### Claim 2（辅）：读取时裁决优于写入时裁决
- **最小实验**：同一批带 slot 的记录。
  - 写入时裁决：每个 slot 只保留最新说法，被作废的不给读者看。这模拟 Mem0、Graphiti 的设计。
  - 读取时裁决：CCR。
- **指标**：同上，重点看矛盾和知识更新。
- **预期**：矛盾类上读取时裁决明显更好，知识更新类相当。

### 规模和第二数据集
- BEAM-1M 40 题、LongMemEval-S 62 题。目标：超过各自数据集上最好的记录检索基线（1M 上 63.3），方向与 100K 一致。

## Experiment Handoff Inputs
- **必须证明**：Claim 1 的 ③ > ①、③ > ②；Claim 2。
- **必须跑的消融**：④ 去闭包，⑤ 去成链，链预算 B_chain，slot 粒度（议题表大小 N）。
- **风险最高的假设**：
  1. 编码器能给出一致的 slot。用矛盾和知识更新题的人工抽查先验证；
  2. 闭包带来的额外链不会挤掉其他题型的证据；
  3. BEAM 的矛盾题是人为埋的，需在 LongMemEval 的知识更新类上确认真实场景也有效。

- **答题**：每个条件 120 题 × 3 次生成。
- **时间线**：
  - 10-16：slot 编码和一致性抽查（先做这一步，过了再往下）；
  - 10-16、10-17：Claim 1；
  - 10-17：Claim 2；
  - 10-18：1M 和 LongMemEval。
