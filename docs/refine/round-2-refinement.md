# Round 2 Refinement

## Problem Anchor（与 round 0 原样相同）
- **根本问题**：在很长的多会话对话里（BEAM 100K/1M、LongMemEval-S，10 万到 100 万 token），让一个固定的 LLM 读者正确回答依赖历史信息的问题，包括抽取、更新、矛盾、时间、排序、摘要等能力。
- **必须解决的瓶颈**：现有做法丢分，主要不是因为信息没存下，而是读者用不上。
  - 100K 上全上下文 74.4 分，丢的 25.6 分全部是“信息就在上下文里，但答案没用上”。
  - Hindsight 给读者 125K 字，丢分里有 17.8 分属于同类。
  - 把原文还给读者（H33）反而掉 9.7 分（p=0.004）。
  - 另一方面，压成 8K 的记录又会丢掉细节和全局脉络：记录检索的丢分里，写入阶段占 15.7 分，信息抽取 70.8 分（逐字检索是 92.0），摘要 39.6 分（全上下文是 53.9）。
  - 召回的“广”和读者的“窄”现在是绑在一起的：要么给多、读者淹没，要么给少、信息缺失。
- **非目标**：
  - 不训练模型；
  - 不追求更大的上下文窗口；
  - 不做新的检索器或向量模型；
  - 不做 agent 式多轮工具调用；
  - 不以 LoCoMo 为主战场（已经饱和）。
- **约束**：
  - 只用 API 模型。实验读者和判分统一用 gpt-6-luna（Pro 代理）；向量用 H20 上的 qwen3-embedding-8b。
  - 开发集：BEAM-100K 120 题、BEAM-1M 40 题、LongMemEval-S 62 题。测试集在方法定型前不碰。
  - 噪声：BEAM-100K 120 题单次生成，95% 区间约 ±5 分。方法比较要做 3 次生成。
  - 目标 ICML 2027，2027-01 下旬截稿。
- **成功条件**：
  1. 在同一读者、同一判分下，读者看到的上下文 ≤8K 字时，BEAM-100K 上超过全上下文（74.4）；
  2. BEAM-1M 上明显超过 Hindsight 和逐字检索；
  3. LongMemEval-S 上方向一致；
  4. 有消融证明提升来自机制本身，而不是来自更多上下文或更多调用。

## Anchor Check
- **原始瓶颈**：证据覆盖与读者可用性之间的取舍。CCR 针对其中“同一件事的多个说法”这一块。
- **仍然针对它**：是。四项成功条件全部保留、全部要报告。矛盾、更新、排序只用来解释机制，不替代总分。
- **拒绝的偏移**：无。

## Simplicity Check
- **主贡献**：最小的“议题键”接口，加上以完整链为单位的打包；写入时不做任何有效性判定。
- **删去**：
  - 端点截断式溢出规则（与“完整”保证矛盾），只收完整的链；
  - 题型提示的特殊措辞，读者提示对所有条件统一；
  - “写入时裁决 vs 读取时裁决”的大结论，改为两个受控对照，不作头条主张。
- **拒绝的复杂化**：不建图、不建边类型、不给路径打分（TRACE 的做法），不做第二轮编译。
- **仍是最小够用**：写入多一个字段，读取多一次查表和打包，没有额外 LLM 调用。主张也随之收窄为：这个最小接口在 BEAM 上就足够，并且不比带有效性判定的重结构差。

## Changes Made
### 1. 议题键的语义单位和身份规则（审稿 #1）
- **单位**：一个“可变命题”，即一个在某时刻只有一个答案、但可以随时间变化或被前后矛盾地陈述的问题。例如：“Darryl 是否在网上买过球鞋”“Foot Locker 之行的时间”“遗嘱执行人是谁”。
  - 事件线（多步事件的先后）不在 slot 的语义里。事件排序不作为 CCR 的目标能力，照常报告。
- **身份**：
  - 稳定 id（S0001…）加一句规范化的命题陈述。
  - 写入时编码器看到候选 slot 表：按本段文本与 slot 陈述的向量相似度取 top 20，加最近使用的 10 个，去重；超过的不显示。
  - 规则：是同一个命题就复用 id；否则新建 id 并写出命题陈述。
  - 一条记录最多挂 2 个 slot。
  - 实体消歧（谁是谁）沿用现有消歧状态；判定哪个说法为真，一律不做。
- **双向审计**：
  - **漏并**：同一命题分到两个 slot。用矛盾和知识更新题检查，开发集 24 题，人工核对。
  - **误并**：一个 slot 里混了不相关的命题。抽 50 个最大的 slot 检查。
  - 两者都报告比率。

### 2. 打包契约（审稿 #2）
- 链按 slot 在种子排名中首次出现的顺序排；能完整放进剩余预算的链才收，放不下的跳过，接着试下一条；记录被跳过的链和长度。
- **保证（有条件的）**：对每个被收入的 slot，账本里该 slot 的所有记录都在上下文里。
- 链内按说话时间排序，同日按来源轮次排；每条标说话日期、事件日期（明说才有，否则留空）、说话人、来源 id。所有元数据都计入 8K 预算。
- 收完链以后，剩余预算按原排名补散条记录（与记录检索相同）。

### 3. 相关工作重写（审稿 #3）
- **TRACE**（2607.00339）：
  - 事件图，包括更新、矛盾、因果等边，路径打分；
  - 更新在写入时把旧事件有效性置 0；矛盾保留但在打分中被惩罚；
  - 评测在 LoCoMo 和 LongMemEval-S，LongMemEval-S 上更新检测关闭；未用 BEAM。
- **Graphiti/Zep**：双时间边，作废但保留历史；**Mem0**：UPDATE/DELETE，图版本标作废。**LeanMem**：时间顺序呈现事件证据。**TOKI**：写入时裁决、保留审计行。
- **我们的位置**：最小接口，写入时只标“同一命题”、不判有效性；在 BEAM（专门考矛盾、更新、排序）上，受控比较“同一账本、同一召回下”的三种做法：
  1. 不加结构；
  2. 写入时有效性标注，保留历史但标出谁被取代（模拟 TRACE、Graphiti）；
  3. 只给命题分组、由读者裁决（CCR）。
- **可能的贡献**：结构可以小到一个键；写入时判有效性在 BEAM 的矛盾题上会系统性出错，因为矛盾和更新在写入时无法区分。这一点必须由结果支持，现在不作断言。

### 4. 验证（审稿 #3、#4）
- **账本**：用一次重编码得到带 slot 的账本，冻结；所有读取对照都在这同一账本上，同一规划、同一种子排名。原流水线（旧账本）只作端到端参照。
- **对照**（同一账本）：
  - A 种子平铺（记录检索）；
  - B 闭包平铺（扩展后的同一批记录按排名平铺）；
  - C CCR（同一批记录按链呈现）；
  - D 有效性标注（同一批记录成链，但每条旧说法标“已被 Sx 取代”。由一次写入时 LLM 判定产生，模拟 TRACE、Graphiti）；
  - E 只留最新（标为“有损消融”）；
  - F 通用压缩 RTC，输入为 B 的扩展集，含同样的元数据。
  - 比较关系：B 对 A 测“补回证据”，C 对 B 测“呈现方式”（记录 id 相同），C 对 D 测“写入时有效性判定”，C 对 F 测“结构 vs 通用压缩”。
- 读者提示对所有条件完全相同，不给 CCR 特殊说明。
- 3 次生成，按对话聚类的配对检验；报告每题输入、输出 token，以及写入时 slot 表带来的额外输入 token。
- 诊断附原文例子和分母：矛盾题 12 道、24 个评分点。
- **门槛**：如果 C 对 A 在 120 题 × 3 次生成上不到 +3，或者矛盾、知识更新两类不升，停止 CCR，回到方法树重新选。

## Revised Proposal（完整版）

### Title
最小命题键：写入时不裁决、读取时成链的对话记忆（CCR）

### Problem Anchor
（同上，原样。）

### Technical Gap
- 对话里同一个命题会被多次陈述，有更新、改口、前后矛盾。BEAM 专门考这一点。
- **现有做法分两类**：
  - **不加结构**（逐字检索、记录检索、Hindsight 事实）：同一命题的说法分散，召回不全，读者看不出它们是同一件事。
    - 我们的诊断：记录检索在矛盾题上，两边都在却被读者自行裁决的 10 个评分点；事件排序丢在召回的 12 个。
  - **重结构加写入时有效性判定**（TRACE、Graphiti、Mem0）：要建图、分类边、写入时判定谁取代谁。可写入时无法区分“改口”和“矛盾”，因为两者都表现为与旧说法不一致。一旦判错，读者看到的就是错误的有效性。
    - 我们的编码器里同样存在写入时裁决：矛盾题有 10 个评分点因为一边没写下而丢分。
- **缺的东西**：一个最小的接口，只表达“这些说法在讲同一个命题”，不表达谁对谁错；读取时据此把整条说法交给读者。

### Method Thesis
- 写入时只给每条说法挂上它所属的“可变命题”键，永不判定有效性；读取时按键闭包、以完整链为单位打包，把裁决留给读者。
- 主张：这个最小接口在 BEAM 上至少与写入时有效性判定一样好，在矛盾类上更好；整体超过不加结构的记录检索。

### Contribution Focus
- **主贡献**：CCR，即命题键接口加完整链打包。
- **辅助**：在同一账本上，受控比较“不加结构 / 写入时有效性 / 读取时裁决 / 通用压缩”。
- **不是贡献**：账本、出处、多路检索、时间图。

### Proposed Method
- **写入**：现有编码提示加两条：
  1. 每条记录给出 slot（复用候选表中的 id，或新建 id 加命题陈述）；
  2. “不要判断哪个说法正确，不要省略与先前不一致的说法，两边都写成记录”。
  - 候选表大小 30（相似度 top 20 加最近 10）。
- **读取**：
  1. 规划和种子召回同记录检索；
  2. 种子按排名取 slot；
  3. 对每个 slot 取账本全链；
  4. 能完整放下的链按序收入，放不下的跳过并记录；
  5. 余下预算补散条；
  6. 统一读者提示。
- **成本**：写入调用数不变，输入多出候选表（约 30 行）；读取不增加调用。
- **失败与诊断**：
  - 漏并、误并比率；
  - 被跳过的链的比例；
  - 写入时一边是否被省略（erran 的写入类）；
  - 读者拿到全链后仍裁决错，计为方法失败，照实报告。

### Claim-Driven Validation
- **Claim 1**：同一账本上，C（CCR）> A（种子平铺），且 C ≥ F（通用压缩）。提升来自矛盾和知识更新，其他能力不降。
- **Claim 2**：C ≥ D（写入时有效性），在矛盾类上 C > D。E（只留最新）作为有损下界。
- **规模**：BEAM-1M、LongMemEval-S 复验；成功条件 1–4 全部报告，包括与全上下文 74.4 的差距。
- **门槛**：先做 slot 一致性审计和 A/B/C 三个条件（1 次生成）。C − A < +3 且矛盾类不升，就停。

### Compute & Timeline
- 重编码 6 段，约 300 次调用；每个读取条件 120 题，不额外调用编码。
- 10-16：编码、审计、A/B/C；
- 10-17：D/E/F 和 3 次生成；
- 10-18：1M 和 LongMemEval。
