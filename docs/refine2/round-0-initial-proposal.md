# Research Proposal：先覆盖、再细化——按问题范围选分辨率的对话记忆（Cover-then-Refine, CTR）

写于 2026-10-16（美东）。证据全部来自开发集（BEAM-100K 10 段 200 题、BEAM-1M 5 段 100 题；3 次生成，按对话聚类的配对 bootstrap），测试集未碰。

## Problem Anchor
- **根本问题**：很长的多会话对话（10 万到 100 万 token），一个固定的 LLM 读者要回答依赖历史的问题。问题类型既有“点”（某个值、某次计划、有没有说过），也有“面”（某个主题这几个月按什么顺序发展、整个过程的总结）。
- **必须解决的瓶颈**：每种现有记忆只用一种分辨率存和给。
  - 逐字检索（原话）：细节最好（信息抽取 1M 86.5），面状题最差（事件排序 1M 25.0、摘要 37.5）。
  - 记录检索（LycheeMemory 式原子记录，8K）：中间。1M 最大丢分是检索（15.4/100 题），集中在面状题：承载信息的记录在排序里中位约 200 名，视图只显示约 12 条。
  - Hindsight（事实 + 观察，约 12.4 万字给读者）：面状题较好（摘要 1M 59.3），但上下文是我们的 3 倍以上，读者“信息在却没用上”的丢分 19.6/100 题。
  - 加预算不解决：记录检索 8K → 2 万字，100K 只 +1.6，1M 更差；把原话回填（H33）−9.7。
  - 结论：覆盖范围和细节分辨率被同一个预算绑死，而不同问题需要的范围差几个数量级。
- **非目标**：不训练；不做更长上下文；不做新的向量模型；不做多轮 agent 工具调用；不以 LoCoMo 为主战场。
- **约束**：只用 API 模型。读者、编译、判分都用 gpt-6-luna（Pro 代理）；向量用 H20 上的 qwen3-embedding-8b。目标 ICML 2027（2027-01 下旬截稿）。工作方式：先小试，有起色再放大。
- **成功条件**：
  1. BEAM-1M 上明显超过 Hindsight（配对显著），读者上下文不超过 Hindsight 的 1/2；
  2. BEAM-100K 上不低于全上下文（69.9）；
  3. LongMemEval-S 方向一致；
  4. 消融证明增益来自“按范围选分辨率”这个机制，而不是来自更多上下文或更多调用。

## Technical Gap
- **现有系统都是单分辨率**，或者多分辨率但按相似度混取：
  - RAPTOR 的“collapsed tree”把各层摘要和原文块放进同一个相似度排序里取前 k，不知道问题需要多大范围；
  - GraphRAG 的 local / global 搜索是两套独立管线，global 用社区摘要做 map-reduce，代价大，也不细化；
  - LightRAG 的双层关键词同样按相似度取；
  - Hindsight / Mem0 / Zep 给事实或观察，只有一种粒度。
- **我们已经看到的事实**：
  - 只给面状视图（8K 全用话题行）：1M 面状题 +10.1，但 100K −12.6，丢了细节；
  - 细记录 + 话题行：两个规模都不吃亏（1M +6.7，p=0.004；100K +0.9）；
  - 面状视图用到所有题：两个规模总分都降（1M −1.0，100K −2.5），点状题丢细节、拒答题被误导；
  - 按题面把面状题分出来后，再给方面摘要全集：1M 总分 +2.5，p=0.016。
  - 所以需要的不是“多加一层摘要”，而是**读取时先决定问题覆盖多大范围，再在那个范围内给能放下的最细分辨率**。
- **缺的机制**：一个从问题估计“范围”（覆盖账本里哪些方面）的步骤，加上一个统一的装配规则，使点、面问题走同一条路径，不需要二分路由。

## Method Thesis
- **一句话**：把同一段历史编译成多个分辨率（原话 → 原子记录 → 方面时间线），回答时先用最粗的、能盖住问题范围的一层把范围盖全，再把剩余预算按相关性用更细的层填满。
- **为什么最小**：账本和记录沿用现有 Lychee-lite；方面层是一次离线编译（每段对话约 1 + 方面数次调用），读取时只多一次范围选择调用。没有训练，没有图，没有多轮 agent。
- **为什么是现在**：LLM 能可靠地做两件以前要专门模型的事：把几百条记录压成带日期的方面时间线；从几十个方面名里判断一个问题覆盖哪些。

## Contribution Focus
- **主贡献**：范围匹配的分辨率选择（cover-then-refine）。在固定读者、相同或更小上下文下，它优于任何单一分辨率的记忆，也优于按相似度混取多层（RAPTOR 式）。
- **辅助贡献（可选）**：方面时间线层——从只追加账本重编译（不自我改写），每个方面一段带日期的“首次出现 → 关键步骤 → 最后状态”。
- **不是贡献**：账本本身、原子记录（来自 LycheeMemory）、读取时冲突检查（RAG 已有，作为对所有方法都加的公共部件）、混合检索。

## Proposed Method
### Complexity Budget
- **冻结 / 复用**：gpt-6-luna 读者；Lychee-lite 分段与记录编码；lychee 的规划与多路检索（向量 + BM25 + 时间过滤，RRF 融合）；qwen3-embedding-8b。
- **新增（都不训练）**：
  1. 方面编译（离线）；
  2. 范围选择（每题一次 LLM 调用）；
  3. 装配规则（确定性代码）。
- **刻意不用**：图数据库、边类型、社区检测、多轮检索 agent、学习型路由、写入时有效性判定（CCR、写入时不裁决都已失败）。

### System Overview
```
写入（离线，只追加）
  对话 ──分段──> L0 原话轮次
           └─编码──> L1 原子记录（带日期、实体、话题、来源轮次）
                         └─方面编译──> L2 方面（名 + 成员记录 + 首次日期 + 带日期摘要）
读取（每题）
  问题 ──范围选择(LLM, 看问题 + L2 方面名列表)──> 覆盖集 A(q)（0 到全部方面）
       ──装配──> [A(q) 的 L2 摘要，按首次日期] + [L1 记录，按 RRF 排名，优先 A(q) 内] + [L0 原话尾巴]
       ──读者（统一提示；所有方法都加读取时冲突检查）
```

### Core Mechanism
- **范围选择**：输入 = 问题 + 本段对话的方面名列表（50–90 个，约 2–4K 字）+ 每个方面的首次日期和记录数。输出 = 问题需要覆盖的方面集合 A(q)，允许为空（纯点状问题）或很大（“整个项目的总结”）。
  - 这把现在的二分路由（点 / 面）换成连续的范围估计。点状问题通常 0–2 个方面，面状问题几十个。
- **装配规则**（预算 B_fine = 8K 字给细层，粗层按需）：
  1. 粗层：A(q) 中所有方面的摘要，按首次日期排序，全部放入（这是“覆盖”保证：被选中的范围一个不漏）。粗层上限 B_max（例如 3 万字），超出时按方面的 RRF 分数截断，并记录被截断的比例。
  2. 细层：lychee 排序中的记录填满 B_fine；属于 A(q) 的记录优先（稳定排序：先 A(q) 内按原排名，再其余按原排名）。
  3. 原话尾巴：与 lychee 相同的 BM25 原话匹配，占细层最后约 1500 字。
  - |A(q)| = 0 时就是原来的 lychee 8K 视图，所以点状问题不受损（H35b 的失败模式被排除）。
- **为什么是主要新意**：选择单位是“问题覆盖的范围”，不是“与问题相似的片段”。多分辨率方法（RAPTOR、GraphRAG、LightRAG）按相似度或按固定的两条管线取层；CTR 先显式估计范围再按“盖全 + 最细”装配，并且点、面问题走同一条路径。

### Optional Supporting Component：方面时间线
- 输入 = 账本记录；每段对话一次调用把话题标签归并成方面（话题多时分块，覆盖率不足自动重试），每个方面一次调用写 ≤400 字带日期摘要。
- 从账本重编译，不对自身改写，可随账本增长按方面增量重编译（只重编被新记录触碰的方面）。
- 已有实例：1M 每段 49–94 个方面、全集 2.6–4.9 万字；100K 每段 14–34 个方面、0.65–1.7 万字。

### Modern Primitive Usage
- LLM 当编译器（方面归并与摘要）和范围估计器（读取时一次调用）。两者都是零样本提示，effort low。
- 比传统做法自然：方面归并若用聚类（向量阈值）会把“API 限流”和“API 性能”这类近义但不同的线索合并或拆散；范围估计若用相似度阈值无法区分“问一个值”和“问整个过程”。

### Integration
- 挂在 lychee 读取管线之后、读者之前；读者提示不变。冲突检查对所有方法（包括 Hindsight、全上下文）同样施加，作为公共部件。

### Training Plan
- 无训练。所有提示固定；开发集只用于选两个超参（B_max、范围选择提示），测试集方法冻结后只跑一次。

### Failure Modes and Diagnostics
- **范围漏选**（面状题只选了几个方面）：报告 A(q) 大小分布；对事件排序、摘要题，统计评分点所在方面是否在 A(q) 中（用已有的“评分点 → 记录”定位工具）。
- **范围误选**（点状题选了很多方面，细节被稀释）：点状题 |A(q)| 分布；与 lychee 的配对差按 |A(q)| 分桶。
- **方面摘要丢细节**：面状题中“信息在上下文但读者没用上 / 信息不在”的划分（erran）。
- **方面编译解析失败**：已遇到一次（1M 第 0 段），覆盖率 < 80% 自动重试。

### Novelty and Elegance Argument
- 最近工作：RAPTOR（多层摘要树 + collapsed tree 相似度取）；GraphRAG（local / global 两套管线）；LightRAG（双层关键词）；Hindsight（事实 + 观察 + mental model）；MemTree；ReadAgent（gist + 回看原文）。
- 差别：CTR 的选择变量是问题的范围（哪些方面必须盖全），再在剩余预算里按相关性给最细层。点、面问题统一，退化情况就是普通记录检索。论文的核心对照是“同一组多分辨率层，按相似度混取 vs 按范围先盖后细”，这样增益只能来自选择机制。

## Claim-Driven Validation Sketch
### Claim 1（主）：按范围先盖后细优于单分辨率和相似度混取
- 实验：BEAM-1M 5 段 100 题、BEAM-100K 10 段 200 题，3 次生成；LongMemEval-S 62 题 1 次生成看方向。
- 对照（同一读者、全部加冲突检查）：
  - 单分辨率：逐字检索 8K、记录检索 8K、记录检索 2 万字、Hindsight（约 12.4 万字）、全上下文（100K）；
  - 同层相似度混取（RAPTOR collapsed-tree 式：L0/L1/L2 统一向量排序，取到与 CTR 相同的字数）；
  - CTR。
- 指标：总分；面状 / 点状分开；每题上下文字数。
- 预期：CTR 1M 上超过 Hindsight（≥ +3，配对显著），上下文约其 1/3；100K 不低于全上下文；相似度混取在面状题上明显低于 CTR。

### Claim 2（辅）：范围估计是必要的
- 消融（1M + 100K，可只 1 次生成）：
  - 二分路由（当前 sys：面 → 方面全集）；
  - 无范围选择（所有题都给全集 + 8K 细层）；
  - oracle 范围（用评分点定位到的方面，作上限）。
- 预期：CTR ≥ 二分路由，且点状题不降；无范围选择在点状题上降（已在 H35b 观察到同类现象）。

## Experiment Handoff Inputs
- 必须证明：Claim 1（尤其对相似度混取的对照）。
- 必须消融：范围选择 vs 二分路由 vs 无选择；粗层上限 B_max。
- 数据：BEAM-100K / 1M 开发集、LongMemEval-S 开发集；最终在测试集各跑一次。
- 风险最高的假设：范围选择器在点状题上能稳定给出很小的 A(q)；方面摘要的细节损失不抵消覆盖收益（H36 8K 内只 +1.6）。

## Compute & Timeline Estimate
- 无 GPU 训练；H20 只做向量。
- 方面编译已完成（1M 5 段、100K 10 段）。范围选择每题 1 次调用；3 次生成 × 300 题 ≈ 900 次读者调用 + 300 次范围调用。
- 10-17：范围选择实现 + 小试（1 次生成，面状 + 点状各 20 题）；有起色后 10-18 跑 3 次生成和相似度混取对照；10-19 LongMemEval-S。
