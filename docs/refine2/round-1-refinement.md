# Round 1 Refinement

写于 2026-10-16 美东。本轮按审稿意见改了定义、预算和相关工作，并先跑了审稿人要求的决定性对照。对照的结果否定了初稿的主贡献，所以主张收窄。

## Problem Anchor（与 round 0 原样相同）
- **根本问题**：很长的多会话对话（10 万到 100 万 token），一个固定的 LLM 读者要回答依赖历史的问题。问题类型既有“点”（某个值、某次计划、有没有说过），也有“面”（某个主题这几个月按什么顺序发展、整个过程的总结）。
- **必须解决的瓶颈**：每种现有记忆只用一种分辨率存和给。
  - 逐字检索（原话）：细节最好（信息抽取 1M 86.5），面状题最差（事件排序 1M 25.0、摘要 37.5）。
  - 记录检索（LycheeMemory 式原子记录，8K）：中间。1M 最大丢分是检索（15.4/100 题），集中在面状题：承载信息的记录在排序里中位约 200 名，视图只显示约 12 条。
  - Hindsight（事实 + 观察，约 12.4 万字给读者）：面状题较好（摘要 1M 59.3），但上下文是我们的 3 倍以上，读者“信息在却没用上”的丢分 19.6/100 题。
  - 加预算不解决：记录检索 8K → 2 万字，100K 只 +1.6，1M 更差；把原话回填（H33）−9.7。
  - 结论：覆盖范围和细节分辨率被同一个预算绑死，而不同问题需要的范围差几个数量级。
- **非目标**：不训练；不做更长上下文；不做新的向量模型；不做多轮 agent 工具调用；不以 LoCoMo 为主战场。
- **约束**：只用 API 模型。读者、编译、判分都用 gpt-6-luna（Pro 代理）；向量用 H20 上的 qwen3-embedding-8b。目标 ICML 2027（2027-01 下旬截稿）。工作方式：先小试，有起色再放大。
- **成功条件**：
  1. BEAM-1M 上明显超过 Hindsight（配对显著），读者上下文不超过 Hindsight 的 1/2；
  2. BEAM-100K 上不低于全上下文（69.9）；
  3. LongMemEval-S 方向一致；
  4. 消融证明增益来自“按范围选分辨率”这个机制，而不是来自更多上下文或更多调用。

## Anchor Check
- 原始瓶颈：覆盖与细节被同一个预算绑死。
- 修订后仍针对它：读者看到“与问题相关的方面的整条时间线”（覆盖）加上 8K 细记录（细节），两者分开计量。
- 被拒绝的偏移：无。审稿人确认 anchor 允许超过 8K，只要不超过 Hindsight 的 1/2。

## Changes Made

### 1. 决定性对照已跑：覆盖保持分配不成立（审稿 CRITICAL #1、#3）
- 审稿人说：中心问题应是“在有限细节预算里，显式保证每个选中方面都分到证据，是否优于按相关性挑”。要求同 A(q)、同候选、同排序、同预算下对比。
- 做法：ctr_cov vs ctr_rel，同一次方面选择（同提示、命中缓存）、总预算 2 万字、先放每个选中方面的摘要（各截到 1 万字 / |A(q)|），剩余放记录，按日期展示，末尾同样的冲突检查。cov 轮流从全局相关列表和每个方面自己的记录列表取；rel 只按全局相关性取。
- 结果（BEAM-1M 100 题，1 次生成）：cov 68.9，rel 68.8，胜负 18:17；面状题 62.7 vs 63.5；点状题 72.6 vs 71.9。
- 结论：分配方式不起作用。按审稿人的建议，不再把贡献归于“分辨率 / 覆盖分配”。

### 2. A(q) 的定义改为“需要其整条历史作为上下文的方面”（审稿 IMPORTANT）
- 小试（ctr v1，1M 100 题，1 次生成）里，选择器对多数点状题选了 2–5 个方面；这些题反而涨了：拒答 57.5（二分路由版 47.5）、矛盾 56.2（48.8）、知识更新 80.0（70.0）、时间推理 90.0（87.5）。
- 解释：问“现在的值”“有没有矛盾”“有没有提过”，都需要知道这件事的来龙去脉；方面时间线正好给出一件事从首次出现到最后状态的变化。
- 修订：A(q) = 读者需要其历史脉络的方面，点状题一般非空；|A(q)| = 0 时退回 lychee 8K + 冲突检查。

### 3. 预算与拼接（审稿 CRITICAL）
- 固定为 v1 形式：细层 8K（lychee 视图，含原话尾巴）+ 粗层（A(q) 各方面摘要全文，按首次日期），粗层上限 3 万字，超出时每个方面等比截短而不是丢方面，并报告截短比例。
- 理由：v2 的 2 万字统一预算对不同题型方向相反（面状 +4，点状 −3.7，时间推理 −20/−10，信息抽取 +13），总分持平；v1 的分开计量更简单，且点状题更好。总上下文中位约 8–13K 字（点状），面状 15–37K 字，均低于 Hindsight 的 1/3。

### 4. 相关工作改写（审稿 Contribution Quality）
- RAPTOR：除 collapsed tree 外还有自顶向下遍历（宽度、深度可控），“先粗后细”本身不是区别。
- ReadAgent-P：一次调用从 gist 里选多个页面展开；CTR 的方面选择与之同形。
- GraphRAG DRIFT：从社区报告出发，再用局部搜索细化，迭代进行。
- LightRAG：问题中抽宽、细两类关键词做双层检索；Hindsight：观察与事实并存，多抽象层。
- Adaptive-RAG：按问题复杂度选检索策略；MemTree：对话的层次表示。
- 我们的位置（收窄后）：机制形态接近 ReadAgent-P / DRIFT，不主张选择或多层表示本身新。可能的新东西只剩两点，需要实验支持：
  1. 对话记忆里的“方面时间线”（同一件事在几个月里的变化，带日期、保留前后矛盾和未确认状态）作为读取单元，对**状态类点状问题**（当前值、矛盾、是否提过）也有帮助，而不仅是摘要类问题；
  2. 时间线只从只追加账本重编译，避免自改写记忆的漂移（H12、H24 已证实漂移）。

### 5. 验证（审稿 Validation）
- 对照改为在同一套存储表示上：
  - lychee_cf（无方面）；
  - ReadAgent-P 式：一次调用看方面名 + 摘要，选要展开的方面，展开为这些方面的全部记录（同字数）；
  - ctr（方面摘要 + 8K 细层）；
  - 仅方面摘要（无 8K 细层）。
  - 所有条件都加冲突检查，并单独报告冲突检查的增量。
- 统计：每题对 3 次生成取平均，按对话聚类配对，报告每段对话的差；100K“不降”的非劣界限为 −2；oracle 方面只作诊断。
- 冻结后测试集各跑一次（BEAM-100K 10 段、BEAM-1M 测试段、LongMemEval-S 测试部分）。

## Revised Proposal

### Title
按问题选取的事件时间线：对话记忆的读取单元（Scoped Thread Timelines, STT）

### Method Thesis
- 长对话里，一件事（一个方面）会在几个月里被多次提起、更新、反悔。读者答题需要的往往不是“最像问题的几条记录”，而是“相关几件事的整条时间线 + 少量细节”。
- STT：离线把只追加账本的记录归并成方面，每个方面编译成带日期的时间线；回答时一次调用选出问题相关的方面，把这些时间线和 8K 细记录一起给读者，并做读取时冲突检查。

### Contribution Focus
- 主：方面时间线作为读取单元，在状态类点状问题和面状问题上都优于记录检索、优于按相似度混取多层、优于 Hindsight，且上下文约为 Hindsight 的 1/4–1/3。
- 辅：时间线只从账本重编译（对比自改写的观察 / 摘要，漂移已在 H12、H24 证实）。
- 不是贡献：方面选择这个调用形态（同 ReadAgent-P）、冲突检查（RAG 已有）、原子记录（LycheeMemory）。

### Method
- 写入：Lychee-lite 分段编码 → 原子记录；每段对话一次调用把话题归并成方面（覆盖率 < 80% 重试）；每个方面一次调用写 ≤ 400 字带日期时间线（首次出现、按时间的关键变化、最后状态，保留不一致）。
- 读取：方面选择（问题 + 方面名、首次日期、记录数）→ A(q)；上下文 = A(q) 的时间线（按首次日期，上限 3 万字，等比截短）+ lychee 8K 细视图；冲突检查（一次调用）附在末尾；统一读者提示。
- 增量维护：新会话的记录只触发其所属方面的时间线重编译。

### Claim-Driven Validation
- Claim 1：STT > lychee_cf，且 ≥ ReadAgent-P 式展开（同表示、同调用数），1M 上 > Hindsight（配对显著）。
- Claim 2：增益同时来自状态类点状题（拒答、矛盾、知识更新、时间推理）和面状题；“仅时间线”和“仅细记录”都比两者合用差。
- 当前证据：1M 1 次生成 ctr 69.5，lychee_cf 64.6，hindsight 63.7；状态类点状题 +7～+10。100K 小试在跑。
