## 候选：穷举型证据的完整性（Completeness for exhaustive-evidence questions）
- 问题：一类问题的正确答案依赖“全部”相关证据——计数（我一共去了几次）、列举/汇总（我提过的所有预算变动）、最新值（现在的预算是多少）、否定（我从没说过 X 吗）、事件排序。按相似度取 top-k 在原理上给不出完整性：重复历史会让 top-k 塌缩到相似片段，漏一条就数错，且无法证明“没有”。
- 我们的证据：BEAM 面状/汇总题是我们和所有系统的共同短板（测试集 1M 面状 72.6 vs Hindsight 75.3；开发集摘要最弱）；1M 规模下更突出。
- 想法（非参数）：账本只追加，因此可以在写时维护“完整的倒排表”（实体/属性/事件类型 → 全部提及的记录 id，带时间），读时对穷举型问题不做 top-k，而是取出完整列表，用确定性操作（计数、取最新、排序、判空）加 LLM 读取，给出可核对的答案；非穷举型问题走常规检索。
- 和最近工作的区别（待细查确认）：User as Code 需要预先定义类型化状态和规则代码；MemCompile/LazyMem 都是预算内选择，不保证完整；“Don't ask LLM to track freshness”只做冲突/新鲜度。
- 可证伪的小试：BEAM 100K/1M 开发集中汇总、多会话、事件排序、知识更新题；先离线统计现有系统错题里“证据不全”的占比（不花 GPT）；再用开源读者对比 top-k vs 完整列表。
- 停止条件：细查发现已有完整性方法；或错题中“证据不全”占比很低；或小试无提升。

## 第 1 步结论：细读 4 篇最接近的工作（10-23 04:40 ET）
- User as Code（2606.16707）：LLM 从全部事实整体重写类型化 Python 状态（不是增量），作者自认约 100 个会话即到上限（50 万字符输入上限）；读时 [STATE] 截 6000 字 + top-20 事实 + top-10 原文；聚合靠 REPL，只在 100 例合成题上测（99%）；未处理“从未提过”；未测 BEAM。LoCoMo 78.8、LME 83.0（Gemini 3 Flash，同骨干复现）。
- xMemory / Beyond RAG（2602.02007）：四层层级 + kNN 图，预算/覆盖阈值内贪心选择、早停；不保证完整，未单独评计数/列举。
- Don't Ask the LLM to Track Freshness（2606.01435）：BM25 top-10 → LLM 抽候选 → Python max(serial)；只做“当前值”；作者自列失败：“之前的值”、带时间条件的计数、top-10 外的候选。
- MemFail（2605.26667）：按 存储→摘要→检索→读者 归因；无计数、无时间任务；检索是瓶颈时加大 k 有用。
- 结论：问题被多处指出，但“增量维护、对计数/列举/最新/之前/排序/判空给出完整证据、能到 1M 规模、不训练”的方法未见。空白暂时成立。
