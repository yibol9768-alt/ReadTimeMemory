## 2. 从证据里读出来的规律
1. **读者是最后的瓶颈。** Hindsight 1M 丢 36 分里，19.6 分是“信息在上下文里，读者没用上”。全上下文在 100K 丢的 25.6 分全是这一类。所以给更多不一定更好。
2. **不同题型要的东西相反。** 面状题（排序、摘要）要覆盖；细节题（信息抽取）要原话；状态题（矛盾、知识更新）要看到同一件事的前后说法并被提醒冲突。固定一种视图，总会在某类题上吃亏。
3. **写入侧的花样在 BEAM 上收益小**（H33、H34、H38、CCR 都失败）；读取侧的组织有效（面状视图、冲突检查）。
4. **召回深度是公开高分的主要来源之一**，但深召回把负担转给读者，正好撞上第 1 条。

## 3. 融合方案（草案）：深召回 + 读取时编译成证据笔记
- **思路**：把 Hindsight / Memanto 的深召回（覆盖）和 chain-of-note、冲突检查、时间线（组织）合在一起：先取得很深的候选（Hindsight 的约 12 万字上下文），再用一次 LLM 调用，按问题把它编译成一份短的“证据笔记”：相关事实按时间排列、按方面分组、标出冲突和缺失；读者只读这份笔记，或读笔记加少量原文。
- **针对的丢分**：Hindsight 的“信息在却没用上”19.6/100 题；矛盾题；面状题的组织。
- **和已有工作的关系**：编译一步类似 chain-of-note / RECOMP 等查询相关压缩；新意要靠“对话记忆特有的组织方式”（时间线、前后说法、冲突、没提过）和受控证据，而不是压缩本身。之前 refine 第一轮把单纯的读取时压缩（RTC）判为“通用压缩”，这次的不同在于以最强系统的深召回为输入，并把组织方式定死为时间线 + 冲突 + 缺失。
- **小试 H41**（1M 100 题，1 次生成）：
  - hs_note：Hindsight 上下文 → 证据笔记 → 读者只读笔记；
  - hs_note2：读者读笔记 + Hindsight 原上下文；
  - 对照：hindsight、cf_hindsight（同次生成）。
- 有起色再加：用我们的方面时间线替换或补充 Hindsight 的 observations；100K 复验；3 次生成。
